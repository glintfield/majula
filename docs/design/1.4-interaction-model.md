# Interaction model

- Status: Draft
- Owner: dc
- Date: 2026-11-26
- Roadmap job: 1.4 Interaction model (Outpost job
  `glintfield-roadmap-e523e821-579b-47a5-b960-64c288d389c4-8c4dd14d-ef7d-4707-8e69-e4adbe29e856`)

## Context

Majula keeps Outpost's shape: work runs automated, and dc steps in at human gates. In Outpost a gate
is a verdict card. dc approves, or declines with a note, and the note re-runs the author, which
writes a v2 from scratch (`outpost/actions/code/orchestrate-pr/SKILL.md`). An item is a status
page with the session beside it. To ask a gate's author a question, dc either messages the
controller, whose answer lands in a two-line strip, or takes the wheel and hands it back afterwards.

dc talked through these pain points in the session that opened this job. Its closing 21-point
summary is the main source of requirements below, cited as "pain-points session, #N". This doc
decides the replacement before the next step writes the gate and permission-mode state machines,
and before 1.5, 1.8 and 3.7 build on it.

## Goals

- A gate is a conversation with the agent that produced the artifact, which edits it in place.
- Each item is built around the next decision dc has to make and what he needs to make it.
- PR comments come one at a time.
- Action, Ask and Bypass are session modes, and dc can talk to a session in any of them.
- Real back and forth replaces the two-line thinking strip on anything dc interacts with.
- dc is alerted when something is blocked on him, without a push relay.
- Every behavior here is presentation-ready data the server sends. Clients render it and never
  re-derive state.

## Non-goals

- What each mode permits at the gate, how an approved write is pinned, permission requests, and how
  a gate's author is resumed hours later. These belong to 1.8.
- Visual design and mockups. 3.7 owns them.
- Formal state machines. They are the next step of this job.
- Proto messages. They come with later API work, under ADR 0003 and 1.5's conventions.
- A push relay. The roadmap's "Push notifications" decision rules it out for v1.
- Anything that spans servers. The roadmap's non-goals exclude it.
- Version history of an artifact. Only the original and the final matter (pain-points session, #8).

## Design

1.4 owns how gates and modes behave for dc: what he sees, when a mode changes and how a gate
conversation runs. 1.8 owns what each mode permits at the gate, how approved writes are pinned,
permission requests, and keeping a gate's author resumable. Where this doc depends on one of those,
it says "1.8" and stops.

### Gates

A gate holds one artifact for dc to decide on. The kinds are design doc, code spec, implementation
plan, job plan, write draft and reply draft. The first four render as markdown. A write draft
renders its exact payload. A reply renders the prose that will be posted, not a command.

A gate has five parts:

- **Artifact.** Its format, the original body, the current body, a `revision` counter and the hunks
  of its last edit (`lastEdit`).
- **Author.** The session whose turn produced the artifact, and its state: `working`, `idle` or
  `resuming`.
- **Edit lock.** Its holder: `none`, `author` or `dc`.
- **Conversation.** A transcript scoped to this gate.
- **Decision.** `open`, `approved` at a revision, or `abandoned` with a reason.

How a gate conversation runs:

- dc can send a message at any time. If the author is mid-turn, the message queues for its next
  turn.
- The author answers in the conversation, edits the artifact, or both. It edits only through a
  typed `edit_artifact` tool scoped to its own gate.
- Each edit bumps the revision. The server streams the whole artifact plus that edit's hunks, so
  clients animate it (strike out the removal, type in the replacement, then drop the struck text)
  without diffing.
- dc's edit button switches the artifact to plain text and takes the lock. It is refused while the
  author holds the lock. Saving bumps the revision and tells the author what dc changed.
- The author holds the lock for the whole of any turn it is working on, and releases it when the
  turn ends. Its `edit_artifact` is refused while dc holds the lock.
- dc's lock is a lease the client renews while edit mode is open. If the client stops renewing it
  for 5 minutes, the server releases it. The client keeps the unsaved text and offers it back.

The gate ends one of two ways:

- **Approve** is enabled only while the lock is free and the author is idle, and needs presence on
  the device. It carries the revision dc saw. A stale revision is refused, and the client shows the
  newer text.
- **Abandon** takes an optional reason and goes one level up:

| Gate kind                                  | Abandon returns to                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------- |
| Design doc, code spec, implementation plan | The job's planner, which replans the step with the reason                       |
| Job plan                                   | The job's planner                                                               |
| Write draft                                | The drafting session, which continues without the write and receives the reason |
| Reply draft                                | The comment walk, where the comment returns to undecided                        |

When a gate is approved, the server keeps the original and the approved body and discards the
revisions in between. The conversation is kept like any transcript.

A gate dc pre-approved resolves without parking. It shows in the record as settled, never as a
decision. Which gates may be pre-approved is decided by 1.8 and the work engine, not here.

Keeping the author resumable across hours, restarts and devices is 1.8's "cold-resumable gate
authors". This doc only requires that while that happens, the gate shows the author as `resuming`
rather than failing.

### Decision-first items

The server computes one item view for each job and each step. It carries:

- `needsYou`: whether the item is waiting on dc.
- `nextDecision`: a one-line prompt and `allowedActions`. Each action has `enabled` and, when
  disabled, a one-line `disabledReason`.
- `focus`: what the item opens on: `artifact`, `decision` or `status`.
- `activity`: up to four one-line summaries of what the session is doing, including one-line
  summaries of its subagents.
- `mode`: the session's mode.
- Collapsed groups with counts, such as "12 completed steps" or "12 resolved comments".

Collapsed groups are fully loaded. dc can expand any of them and drill in, and expanding animates.
An item that needs dc opens on its focus. One that doesn't shows its state and its live session.

The cockpit groups items as Decide, Broken and Recently cleared, on every client. Outpost only
groups this way on the phone (`outpost/src/pwa/components/cockpit/inbox.js`).

### PR comments, one at a time

A comment walk is a queue over the PR's unsettled comments. A comment that arrives mid-walk joins
the end. Each position shows:

- The comment: its author, body and `path:line`.
- The slice of the diff around it, computed by the server.
- The author's thoughts and a proposed disposition: reply, edit or ignore.
- For a reply, a reply-draft gate.
- The conversation.

dc settles each comment and moves to the next:

- **Reply.** The reply posts as soon as it is approved, as a structured write from the server's
  outbox (1.8).
- **Edit.** The author edits the checkout, and the change joins the walk's pending edits.
- **Ignore.** Nothing is posted.

Under the reply pre-approval, replies post unattended and show in the walk as settled.

At the end, the walk's summary leads to one write-draft gate that commits and pushes all pending
edits. If dc abandons the walk first, the summary lists posted replies whose edits are still
uncommitted.

The server sends the position (i of n), the current comment, the settled count, the pending-edit
count and the uncommitted-reply warning.

### Session modes

A session runs in one of three modes:

- **Action.** Non-interactive. The session runs automated within its action's grants.
- **Ask.** Interactive. Permission prompts show inline in the conversation.
- **Bypass.** Interactive, with no prompts.

dc can message a session in any mode. The mode changes like this:

- dc messaging a session in Action, from a gate or a step, switches it to Ask.
- When the gate resolves, by approve or abandon, the session returns to Action.
- With no gate, a **Done** control returns it to Action, and so does the step's next park.
- Bypass is never turned on automatically. Only dc turns it on, per session, from a client, with
  presence on the device. It clears when the session returns to Action or ends. Resolving a gate
  therefore also ends Bypass.

The mode is server state, sent on the session and item entities. Clients show it plainly, Bypass
most of all. Messaging a session never widens its grants. Which calls prompt in Ask is 1.8's.

Outpost's Drive and Hand back (`outpost/src/pwa/components/work/wheel-toggle.js`) become Action to
Ask and Ask to Action.

### Live session view

- An expanded step keeps today's full session view, with the composer at the bottom
  (`outpost/src/pwa/components/work/orchestrated-card.js`).
- A minimized item shows a 3-4 line activity strip, with no composer.
- A gate shows the artifact beside its conversation on desktop, and stacked on the phone.

### Alerts

The server keeps an `attention` set. Each entry has an item id, a kind, a title and `since`. The
kinds are: a gate is ready, a session in Ask needs a permission, and a step failed and the agent
gave up. Each item alerts once and stays quiet until it resolves. Completions and progress never
alert. Every alert names its server; opening one switches to that profile and opens the item
(roadmap "Multiple servers per client").

- **Mac menu bar.** The primary channel. It shows a badge count for each server profile.
- **iPhone and Android.** In-app badges, and notifications only while the app is in the
  foreground.

Background refresh (BGAppRefresh, WorkManager) is not used for alerts in v1. It runs when the OS
decides, so it would promise alerts it can't deliver.

### Data model and tenancy

The template asks for a `workspaceId` and an owner `userId` on every record. That contradicts the
roadmap's "One person per server" decision: records carry no tenant or owner columns, ever.
`docs/threat-model.md` §1, T5, I5 and I12 still assume tenancy (see Open questions).

This design adds no tenant or owner columns. It records the acting device on every command listed
under API and contract changes (I11).

New records, as shapes only. The jobs that own storage design the tables.

- **Gate.** The artifact's original and current body, its revision, the lock and its lease, the
  author's session, and the decision.
- **Comment walk.** The queue, the position, each comment's disposition, and the pending edits.
- **Attention.** One entry per item that is blocked on dc.

No credentials or integrations are added.

### API and contract changes

The server streams these as small whole entities, as the roadmap's "Client/server contract" asks:

- `Gate`
- `ItemView`
- `CommentWalk`
- `Attention`
- `mode` on `Session`

Client commands:

- `SendMessage`
- `BeginEdit`, `SaveEdit(baseRevision)`, `CancelEdit`
- `ApproveGate(revision)` (presence on the device), `AbandonGate(reason)`
- `SettleComment(disposition)`
- `SetMode` (presence on the device for Bypass)
- `Done`

Author tools: `edit_artifact`, scoped to its own gate, and `answer`.

The names are illustrative. The proto comes later, under ADR 0003 and 1.5's conventions. Nothing
ships yet, so there is no compatibility concern.

## Alternatives

**Outpost's gate card with request-changes.** dc approves or declines with a note, and the author
writes a v2. It is simple and every decision is a clean verdict. But every question costs a full
round trip, which kills iteration (pain-points session, #1). Asking "why X?" means messaging the
controller or taking over (#2). Rejected.

**Direct edit only.** dc edits the artifact himself, with no author in the loop. It is the cheapest
to build and needs no resumable author. But dc can't ask why the author chose something, and every
change is his to make. Rejected; the chosen design keeps direct editing as one half of the gate.

**A fresh session answers questions.** A new session with no stake in the artifact answers dc's
questions, so nothing has to keep the author resumable. But it has to re-derive reasoning it never
had, and its edits drift from the artifact's intent. Fresh context suits review, where the job is to
find errors, not a gate conversation, where the job is to explain decisions. Rejected.

**Live co-editing.** dc and the author type into the artifact at once, CRDT-style. It removes all
waiting. But dc asked for mutual lockout (#6), and Approve needs one stable revision to bind to
(I2). Rejected.

**Take-over as a concept separate from modes.** Outpost's Drive and Hand back, beside the session's
permission mode. It works today, but it puts a manual switch between dc and every question
(#2, #19), and two overlapping concepts make it unclear what a session may do. Folding take-over
into the modes gives one answer. Rejected.

**Chosen:** a gate is a conversation with the artifact's author, who edits it in place under a
single-holder lock, and the gate ends in Approve or Abandon. Asking costs one message, editing
stays possible, and Approve still binds to one revision.

## Testing

This PR is a design doc with no code, so it adds no tests. The design is proven by the next step's
state machines and by 3.7's clickable comment-triage prototype. It adds no T2.n escape to the
corpus. 3.2 should cover an author's `edit_artifact` aimed at another gate, and an approval at a
stale revision.
