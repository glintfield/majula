# 0006. IDs

- Status: Accepted
- Date: 2026-11-26

## Context

Job 2.1 designs the first tables, and every later job adds records that point at each other, so
the ID scheme has to be fixed first. The roadmap's decisions constrain it:

- **One person per server.** Records carry no tenant or owner columns, and commands and approvals
  record the device that acted.
- **Multiple servers per client.** One app pairs with several servers, and no two servers may
  recognize it as the same device.
- **Control-plane spec.** The core addresses repos by `projectKey`, the normalized git remote, and
  machines by `nodeId`, which is `local` in v1.

Outpost's IDs are bare UUIDv4s, so a job ID and a step ID look alike in logs and at the API.
Outpost keys projects by local path, and `projectKey` (`projectKeyFromRemote` in
`src/storage/project-registry.ts`) is its only path-independent identity, which a repo without an
origin lacks. The move from `glintfield/majula` to `noctana/majula` showed that a repo's remote
can change under a checkout that keeps working.

The threat model and the spec template still required `workspaceId` and an owner `userId` on every
record. This ADR retires that; the threat model and spec template change with it.

## Decision

### ID format

- Every record ID the server mints is a [TypeID](https://github.com/jetify-com/typeid):
  `<prefix>_<suffix>`. The prefix is lowercase `[a-z]` with inner underscores, at most 63
  characters, and fixed per record type. The suffix is a UUIDv7 in 26 characters of lowercase
  Crockford base32, starting with `0`–`7`.
- On the wire an ID is a protobuf `string`; in SQLite a `TEXT` column. Byte order follows
  creation time to the millisecond; anything that needs a strict order uses an explicit sequence.
- Every later record type names its prefix in the design doc that introduces it. Prefixes are
  declared once in server code, so a duplicate fails the build, and are never reused.
- IDs are names, not secrets. Knowing one grants nothing.
- Every ID that crosses B1 or B2 is parsed against its type's pattern,
  `^<prefix>_[0-7][0-9a-hjkmnp-tv-z]{25}$`, before use, and a wrong prefix is refused.
- An ID a client mints, such as a command ID for idempotent retry, uses the same format and is
  validated the same way. The command/event ADR owns command IDs.

The prefixes fixed here:

| Prefix | Record                       |
| ------ | ---------------------------- |
| `prj`  | Project                      |
| `dev`  | Device                       |
| `node` | A non-local node (not in v1) |

### Projects and projectKey

- A **project** is a repo the server works in. Its `projectId` (`prj_…`) is minted when the
  project is registered and never changes. Records that refer to a project store `projectId`.
- **`projectKey`** is derived from the project's `origin` remote and is unique among the server's
  projects. The node interface takes it, and it matches a project to GitHub and job sources. It
  can change; `projectId` can't.

The key comes from `git remote get-url origin`, which applies `insteadOf` rewrites:

1. Strip surrounding whitespace. Accept scp-like `[user@]host:path`, `ssh://`, `git+ssh://`,
   `https://`, `http://` and `git://`. Anything else, such as `file://`, a local path or `ext::`,
   is not a usable remote.
2. Drop the scheme, the userinfo (including a token embedded in an https URL) and the port.
3. Strip trailing `/`, one trailing `.git` (case-insensitively) and leading `/`, and collapse
   repeated `/`.
4. Lowercase the host and the path.
5. Require a host matching `[a-z0-9.-]+`, so an IPv6 literal isn't a usable remote, and at least
   two path segments, each matching `[a-z0-9._-]+` and neither `.` nor `..`. GitLab subgroups
   give more than two.
6. The key is `<host>/<path>`.

| Remote                                                       | projectKey                   |
| ------------------------------------------------------------ | ---------------------------- |
| `git@github.com:noctana/majula.git`                          | `github.com/noctana/majula`  |
| `https://github.com/Noctana/Majula`                          | `github.com/noctana/majula`  |
| `ssh://git@github.com:22/noctana/majula.git/`                | `github.com/noctana/majula`  |
| `https://x-access-token:TOKEN@github.com/noctana/majula.git` | `github.com/noctana/majula`  |
| `git@gitlab.com:group/sub/repo.git`                          | `gitlab.com/group/sub/repo`  |
| `git@github-work:noctana/majula.git`                         | `github-work/noctana/majula` |
| `file:///srv/repo`, or no origin                             | `local:<projectId>`          |

- **No usable origin.** The key is `local:<projectId>`. A normalized remote never contains a
  colon, so the two forms can't collide, and a local-only repo matches nothing on GitHub.
- **SSH host aliases aren't resolved.** `github-work` above is the host as written. Job 3.5 can
  resolve `~/.ssh/config` if aliases turn out to matter.
- **Remote changes.** The server reads origin only from the registered path, never from a
  checkout. When it normalizes to a new key, the change is shown to dc and takes effect only once
  dc confirms it from a client; until then the project keeps its old key. A confirmed change
  updates `projectKey` in place and an event records it; `projectId` and its history stay. If
  another project already has the new key, the change is refused. An origin that is removed or
  stops being usable falls back to `local:<projectId>` the same way.
- **One path per key per node.** Registering a second path whose key is already registered on the
  node is refused. Checkouts the server creates aren't projects.
- **A projectKey never becomes a path.** Checkout directories are named from IDs.

### nodeId

- A record tied to a machine, such as a checkout, a session or a step's assignment, carries
  `nodeId`. In v1 it is always `local`, the in-process node, and any other value is refused.
- Multi-machine nodes would get `node_…` TypeIDs. `local` has no `_`, so it can't collide with one.

### Devices and actors

- A **device** is one app's pairing with this server, which the app calls a server profile. The
  server mints its `deviceId` (`dev_…`) when pairing completes. The app sends no device identifier
  before that, so two servers paired with the same app can't tell it's the same device.
- Pairing again mints a new `deviceId`. A revoked one is never reused.
- Device keys, tokens, scopes and revocation, and the server's identity in the pairing payload,
  are job 1.7's. The server's identity isn't a record ID: no record carries it, since everything
  on a server belongs to that server.
- **There is no user, owner or workspace ID.** A server serves one person.
- **Actors.** A command, approval or gate decision records who acted: `device` with the
  `deviceId`, `session` with the agent session's ID for what a session submits, or `server` for
  timers, effects and standing policies. An approval under a pre-approval cites the
  pre-approval's record, which names the device that set it. The command/event ADR places the
  actor in the command envelope.

## Alternatives

- **UUIDv4, Outpost's choice.** Random order fragments indexes, and IDs of different types can't
  be told apart, so passing a job ID where a step ID belongs goes unnoticed.
- **Bare UUIDv7.** Time-ordered, but 36 characters with no type. A TypeID is a UUIDv7 with a type
  prefix and a shorter encoding, and converts back to a UUID where a library wants one.
- **ULID.** Same order and length as a TypeID suffix, but untyped, and its monotonic mode is
  per-process state. TypeID gets the same properties from a standard UUID.
- **SQLite integer row IDs.** Compact, but enumerable, they reveal counts, and a client can't mint
  one for an idempotent retry.
- **`projectKey` as the project's primary key, as Outpost's control-plane spec proposes.** A
  rename or move would rewrite every row that refers to the project, or orphan its history.
- **`deviceId` as a fingerprint of the device's public key.** Rotating the key would change the
  ID, and an app that reused a key across servers would be recognizable.
- **Keep `workspaceId` and `userId` columns with one value each.** They'd prepare for a shared
  server, which the roadmap rules out permanently, and every query and design would carry them.

## Consequences

- Job 2.1 declares the prefixes and the TypeID helpers, and every table keys on TypeIDs.
- Job 3.1's node interface takes `projectKey` and `nodeId`.
- Job 3.5 implements remote normalization, the pending key change and its confirmation from a
  client, with a table-driven test covering the examples above.
- Jobs 1.7 and 2.6 design device credentials around a server-minted `deviceId`.
- The command/event ADR places the actor in the command envelope and defines command IDs.
- Job 7.3's importer maps Outpost's UUIDs and project keys to TypeIDs and normalized keys.
- The threat model retires T5 and I12, and the spec template drops its tenancy prompt.
- Changing the ID format, adding a user or tenant ID, or letting a client choose its `deviceId`
  needs an ADR that supersedes this one.

## Security

This touches T1 × B1, T2 × B2 and T3 × B1.

- **I13, T2.5:** an ID is checked against its type's pattern before use and contains no `/`, `.`,
  `-` or whitespace, so it is safe as a path component or an argument. A `projectKey` never becomes
  a path.
- **I6 (T2 × B2):** an agent that rewrites the registered repo's origin, for example through R1,
  can't retarget the project, because a `projectKey` change waits for dc's confirmation.
- **I8:** an ID is not a credential, and every route still authenticates its caller.
- **I10, I11:** approvals and gate decisions record the acting `deviceId`, and a revoked device's
  ID is never reissued.
- **I7, as a property of how keys are built rather than through these cells:** userinfo is
  dropped from remote URLs, so a token embedded in one never reaches a `projectKey`, a record or a
  log.
- **A client that leaks between servers:** `deviceId` is minted by each server, so no identifier
  links one server profile to another.
- T5 and I12 are retired with this ADR. R1 and R2 are unchanged.
